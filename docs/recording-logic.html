Recording Logic

QuantumQA V2 Recording Engine — Technical Guide

About This Document

This document describes the V2 recording engine, which uses Playwright's native _enableRecorder private API to capture UI interactions and API traffic. Unlike V1 (browser-side JS injection with event listeners), V2 delegates all action capture to Playwright's built-in codegen infrastructure.

Key Concepts:

  • Three Recording Modes: UI Steps, API Requests, All (both simultaneously)
  • Playwright-Native Selectors: Uses InjectedScript.generateSelectorSimple — the same engine as playwright codegen
  • Step Consolidation: Noise reduction via click-before-fill merging, Tab-press filtering, and per-character fill deduplication
  • Environment-Aware API Mapping: URLs split into baseUrl + path for cross-environment reuse
  • Remote Agent Architecture: Recording runs on remote Playwright agents, not the server directly
1. Architecture Overview

The recording engine spans four layers connected via WebSocket:

2. Session Lifecycle

A recording session goes through five clearly defined phases:

flowchart LR A[Init] --> B[Launch Browser] B --> C[Start Adapter] C --> D[Record] D --> E[Stop & Cleanup] style A fill:#ddf4ff style E fill:#dafbe1

Phase 1: Init (recording-control.ts)

  • Server sends RECORDING_START WS message with targetUrl, projectId, agentId, caseId, suiteId, mode, environment, apiFilter
  • Agent sets status to busy and emits RECEIVED status event

Phase 2: Launch Browser (recorder/index.ts)

  • chromium.launch() with headless or headed mode (controlled by HEADLESS env var)
  • browser.newContext() with null viewport (full page)
  • context.newPage() for the recording page

Phase 3: Start Adapter (adapter.ts)

  • PlaywrightRecorderAdapter.start(context) calls context._enableRecorder()
  • Registers two callbacks: onActionAdded and onSignalAdded
  • The adapter is a thin shim that does no browser-side JS injection
  • Playwright handles all event capture internally via its own injected script
_enableRecorder is a private Playwright API. It is not covered by semver guarantees. The project pins Playwright to v1.58.2 for this reason. PlaywrightRecorderAdapter.isAvailable() should be checked before calling start().

Phase 4: Recording

  • Page navigates to targetUrl via page.goto()
  • User interactions are captured by Playwright's internal recorder
  • Actions flow through: adapter → translator → consolidator → emitConsolidatedStep
  • API events (XHR/Fetch) are captured via page.on('requestfinished')
  • Terminal events (page close, crash, browser disconnect) trigger automatic cleanup via handleTerminalClose

Phase 5: Stop & Cleanup

  • stopRecording() flushes consolidated steps, stops the adapter, closes the browser
  • Or: terminal event handler runs on page close / crash / disconnect
  • Session variable set to null; agent status returns to idle
3. The Action Pipeline

Every recorded action passes through a four-stage pipeline before reaching the server:

flowchart LR A[Playwright\nInternal Recorder] -->|ActionInContext| B[translator.ts\ntranslateAction] B -->|RecorderStepPayload| C[consolidation.ts\nStepConsolidator.add] C -->|Buffered & Merged| D[recorder/index.ts\nemitConsolidatedStep] D -->|StepRecordedEvent| E[Server] style A fill:#ddf4ff style E fill:#dafbe1

Stage 1: Playwright Internal Recorder

Playwright's _enableRecorder API emits ActionInContext objects. These are the same data structures that power playwright codegen. Each action contains:

  • frame: page GUID, page alias, frame path (supports iframes)
  • action: discriminated union — click, fill, press, navigate, select, check, uncheck, hover, setInputFiles, assertText/Value/Checked/Visible/Snapshot, openPage, closePage
  • startTime / endTime: timing for each action
  • signals: correlated navigation, popup, download, dialog signals

Stage 2: Translate (translator.ts)

translateAction() maps Playwright's internal ActionInContext into a RecorderStepPayload. The translation normalizes action names, extracts locator information (preferring official Playwright selectors over CSS fallbacks), and preserves frame paths for iframe-aware execution.

Stage 3: Consolidate (consolidation.ts)

StepConsolidator is a stateful buffer that reduces noise in the raw action stream:

RuleDescription
Click-before-fill mergeIf a click is immediately followed by a fill on the same element, only the fill is kept (the click was just to focus the input)
Per-character fill mergeSuccessive press actions on the same input are merged into a single fill action
Tab-press filteringTab key presses are removed — they represent focus changes, not test-relevant actions
DeduplicationDuplicate consecutive actions on the same locator are collapsed

Stage 4: Emit (recorder/index.ts, emitConsolidatedStep)

The final stage builds a stepRecord object (compatible with TestStep contract) and extracts a UIElement from the locator data. Both are emitted via the session callbacks:

  • onStepRecorded(stepInfo) → for server-side step persistence
  • onElementRecorded(element) → for element repository upsert
4. Selector Generation

Playwright's InjectedScript.generateSelectorSimple produces locators in two formats:

KindExampleWhen Used
officialinternal:role=button[name='Login'][i]Preferred — generated by Playwright's internal selector engine
css#login-buttonFallback — minimal CSS when official engine fails

locator.ts processing:

  • locatorRefToName(): Converts a LocatorRef into a human-readable name (e.g., "Login button") for display in the test builder UI
  • locatorRefToLegacyDef(): Converts a LocatorRef into the legacy { selectorType, value } format used by older test execution paths, supporting the selectorType values: getByRole, getByTestId, CSS, getByText
5. API Recording

When recording mode includes api or all, the system intercepts HTTP requests via Playwright's page.on('requestfinished') event.

Filtering Pipeline:

  1. Resource type filter: Only XHR and Fetch requests are captured (not document, stylesheet, image, etc.)
  2. Method filter: OPTIONS preflight requests are ignored
  3. Origin check: By default, only same-origin requests are recorded. Cross-origin requires apiFilter to be set
  4. URL pattern filter: If apiFilter is provided (glob pattern like *api/users*), it's converted to a regex and tested against the request URL
  5. Status filter: Failed responses (status === 0) are ignored

Data captured per request:

  • url: Full request URL
  • method: GET, POST, PUT, DELETE
  • headers: All request headers
  • postData: Request body (if any)
  • status: HTTP response status code
  • projectId: Scoped to the active project

Server-side processing (service.ts handleApiRecorded):

  • Endpoint extraction: URL is split into baseUrl (origin) and path. An endpoint is created or updated with baseUrls: { [environment]: origin } map
  • Query parameters: Search params are extracted and stored on the endpoint
  • Header profile: Request headers (minus browser-internal ones like sec-ch-ua, accept-encoding, etc.) are deduped and saved as a HeaderProfile
  • Body template: If postData exists, it's parsed (JSON or plain text) and saved as a BodyTemplate
  • Step generation: A TestStep of type apiGet/apiPost/apiPut/apiDelete is created, referencing the endpoint, header profile, and body template
  • Assertion: A status code assertion is automatically added (e.g., status === 200)
6. WebSocket Event Protocol

All recording events are wrapped in a RECORDING_EVENT envelope and routed by ws-handlers.ts:

Inner EventDirectionPayload
recorder-state-changedAgent → Server{ status: 'RECEIVED'|'STARTED'|'STOPPED'|'FAILED', caseId?, suiteId?, mode?, message? }
step-recordedAgent → Server{ projectId, stepInfo: { action, element?, dataValue?, step? }, type: 'UI'|'API', caseId?, suiteId? }
element-recordedAgent → Server{ projectId, element: UIElement, caseId?, suiteId? }
api-recordedAgent → Server{ projectId, environment?, apiInfo: ApiRecordedInfo, caseId?, suiteId? }

The server ws-handlers.ts dispatches each inner event to the corresponding service.ts handler function, which persists data to SQLite and broadcasts real-time updates to connected clients.

7. Client-Side Integration

The React client integrates recording through two key modules:

useTestCaseRecording.ts (React Hook):

  • Manages recording state (idle, starting, recording, stopping)
  • Calls POST /api/recording/start and POST /api/recording/stop
  • Listens for WebSocket events and updates TanStack Query cache via queryClient.setQueryData()
  • On step-recorded: appends the new step to the test case's step list
  • On recorder-state-changed: updates recording status indicator

TestCaseRecordingModal.tsx:

  • Target URL input with validation
  • Recording mode selector: UI, API, or All
  • Agent selector via ExecutionTargetSelector (simplified view showing only idle/busy agents)
  • API filter input (glob pattern for URL filtering)
  • Start button that dispatches the recording request
8. Error Handling & Edge Cases

Session Safety:

  • A startingPromise guard prevents concurrent startRecording() calls from racing
  • If startRecording() is called while a session exists, the existing session is stopped first
  • Terminal event handlers (page close, crash, browser disconnect) in handleTerminalClose ensure cleanup even on unexpected failures
  • A closing flag prevents double-close on the same session

Adapter Resilience:

  • PlaywrightRecorderAdapter.isAvailable() feature-detects the private API before use
  • adapter.stop() is best-effort with all errors silently caught
  • Browser close errors (race conditions with headless mode) are caught and ignored

Step Consolidation Edge Cases:

  • Rapid successive keystrokes during fill actions are merged into a single step
  • Click-before-fill on the same element is collapsed (the click was just to focus)
  • Tab key navigation between fields is filtered out
  • Duplicate actions on the same locator are deduplicated

Server-Side Error Handling:

  • Each insertCaseStep call is wrapped in try/catch with error logging
  • Agent disconnection during recording is handled by WebSocket close events
  • If the target agent is not connected or busy, the server returns appropriate HTTP errors (404/409)
9. Limitations & Future Considerations
Known Limitations:
  • Private API dependency: _enableRecorder/_disableRecorder are not part of Playwright's public API. Future Playwright versions may break recording without warning.
  • No local recording: The server explicitly requires an agentId. Single-process (local server) recording is not supported.
  • Step consolidation is agent-side only: If server-side recording is added in the future, the consolidation logic would need to be shared.
  • Module-level session: The recorder currently supports one session at a time per agent process. Multi-session support would require a session map.

Future Considerations:

  • Extract StepConsolidator into the shared/ layer for reuse across agent and potential server-side recording
  • Add graceful fallback to CSS selectors when Playwright's official selectors change format
  • Support multi-tab recording (tracking page switches during a session)
