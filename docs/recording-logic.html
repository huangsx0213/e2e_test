Recording Logic

QuantumQA Unified Recording Engine - Technical Guide

About This Document

This document describes the recording logic of QuantumQA's unified recording engine. The engine captures both UI interactions and API requests while users browse the application.

Key Concepts:

  • Three Recording Modes: UI Steps, API Requests, Elements Only
  • Smart Selector Generation: Automatic best selector choice with live DOM validation
  • Environment-Aware Mapping: API URLs split into baseUrl + path for cross-environment reuse
  • Browser-Side Injection: JavaScript tracker injected via Playwright's addInitScript
1. Recording Entry Point

When a user starts recording from the UI, the system initiates a Playwright browser instance and injects the tracking script.

Entry Process (engine.ts startRecording):

  1. Cleanup Previous Session: If any recording is already active, stop it first to prevent conflicts.
  2. Launch Browser: Start a Chromium browser instance in headless or headed mode based on configuration.
  3. Create Page Context: Create a new browser page context and navigate to the target URL.
  4. Expose Bridge Functions: Expose several functions from Node.js to the browser for communication:
    • onElementClicked - Called when right-click to record an element
    • onStepRecordedAction - Called when left-click to record a UI step
    • onRecorderStateChanged - Called when user toggles recording state
  5. Inject Tracker Script: Add the JavaScript tracker via addInitScript that runs on every page navigation.
  6. Navigate to Target: Finally, navigate to the user-provided target URL.

Three Recording Modes:

💻 UI Steps

Records click, type, hover actions. Left-click on interactive elements automatically captures the action.

🌐 API Requests

Records XHR and Fetch requests. Filters by URL pattern if apiFilter is specified.

📦 Elements Only

Records just the element locators without generating test steps. Right-click on elements to capture.

2. Browser-Side Tracker (Injected Script)

The tracker is injected via Playwright's addInitScript and runs on every page load, including SPA navigation.

Tracker Components:

  1. State Management: Maintains __recorderState with isPaused (boolean) and mode (ui/api/element).
  2. Floating Toolbar: A UI panel in the top-right corner allowing users to switch modes and pause/resume recording.
  3. Badge Indicator: A bottom-center badge showing "Right-Click an element to Record" - shown only in element mode.
  4. Event Listeners: Three types of browser events are monitored:
    • contextmenu (Right-click): Captures element for Elements mode
    • click (Left-click): Captures UI actions in UI mode
    • focusout: Captures TYPE and SELECT_OPTION actions when users finish inputting
  5. State Synchronization: When user changes mode or pauses, the browser notifies the server via onRecorderStateChanged.
The tracker uses setInterval to continuously ensure the toolbar and badge remain visible, handling Single Page Application (SPA) navigations where the page doesn't fully reload.
3. Smart Selector Generation

When an element is captured, the system generates the best possible selector through a priority-based validation system.

Selector Priority (Highest to Lowest):

  1. Role Locator (getByRole): Highest priority. Uses ARIA role and accessible name. Two variants - exact match first, then fuzzy match.
  2. Test ID (getByTestId): Second priority. Uses data-test, data-testid, or data-qa attributes.
  3. ID Locator (CSS #id): Third priority. Uses HTML id attribute, excluding auto-generated numeric IDs.
  4. Text Locator (getByText): Fallback. Uses visible text content, limited to 2-50 characters.

Validation Process:

For each candidate selector, the system validates against the live DOM:

  • Counts matching elements (should be exactly 1)
  • Checks visibility (should be visible)
  • Visual feedback: Pulsing blue outline on matched element

Validation Retry Logic:

If no selectors validate on first attempt, the system waits 60ms and retries once. This handles transient states during page transitions.

Fallback Strategy:

If all validations fail (e.g., due to page navigation mid-validation), the system trusts the highest-priority candidate anyway. This ensures recording doesn't break even in edge cases. The element is marked as isVerified: false in this case.

ARIA Information Extraction:

The tracker calculates ARIA role and accessible name using official browser semantics. Role defaults are inferred from tag name (button, input, select, etc.) if not explicitly set. Accessible name is pulled from innerText, aria-label, placeholder, label, title, alt, or value.

4. Element Recording (Right-Click)

In "Elements Only" mode, right-clicking an element captures its locator for the Element Repository.

Capture Flow:

  1. Event Trigger: User right-clicks on a target element.
  2. Context Menu Prevention: The tracker's contextmenu handler calls preventDefault() to stop the browser menu.
  3. HTML Extraction: Creates a clean clone of the target element (style stripped, text truncated to 50 chars).
  4. ARIA Extraction: Calls getAriaInfo() to get role and accessible name.
  5. Selector Generation: Calls generateSmartSelector() to produce validated locators.
  6. Visual Feedback: Highlights the element with green outline and background for 1 second.
  7. Callback to Server: Calls window.onElementClicked() with the captured element data.

Element Data Structure:

  • id: Unique timestamp-based ID
  • name: Descriptive name from selector
  • selectorType: getByRole, getByTestId, CSS, getByText
  • value: The actual selector value
  • locators: Array of all valid locators (for fallback)
  • description: Human-readable description
  • originalHtml: Raw HTML of the element
  • pageUrl: URL where element was captured
5. UI Step Recording (Left-Click)

In "UI Steps" mode, left-clicking interactive elements automatically records test steps.

Step Types Captured:

  • CLICK: Triggered by left-click on buttons, links, or interactive elements
  • TYPE: Triggered when focus leaves (focusout) an input/textarea with changed value
  • SELECT_OPTION: Triggered when focus leaves a select dropdown with changed value

Action Capture Flow:

  1. Event Detection: The tracker's click and focusout listeners fire.
  2. Interactive Check: Checks if target is interactive (button, a, input, select, textarea, role=button, tabindex).
  3. Value Tracking: For input/textarea, stores original value on focusin. On focusout, compares to detect changes.
  4. Filtering: Skips checkbox/radio click (let change handler manage), skips input focus without value change.
  5. Selector Generation: Generates smart selector for the target element.
  6. Callback to Server: Calls window.onStepRecordedAction() with action type, element data, and data value.
Input elements track their original value on focusin to detect actual changes. This prevents recording empty TYPE steps when users only click into fields without typing.
6. API Request Recording

In "API Requests" mode, the system intercepts XHR and Fetch requests matching the filter criteria.

Interception Flow:

  1. Request Listener: Playwright's page.on('requestfinished') handler processes completed requests.
  2. State Check: Only processes if not paused and in API mode.
  3. Resource Type Filter: Only records XHR and Fetch requests, ignores other types (document, stylesheet, image, etc.).
  4. Method Filter: Ignores OPTIONS preflight requests.
  5. Origin Check: By default, only records same-origin requests. Cross-origin requires apiFilter override.
  6. URL Filter: If apiFilter is provided, matches request URL against the regex pattern.
  7. Status Check: Ignores failed responses (status 0 indicates failure/abort).
  8. Data Extraction: Captures URL, method, headers, postData, and response status.

Environment-Aware Mapping:

When an API is recorded, the system splits the URL into baseUrl and path for cross-environment reuse:

  • baseUrl: The origin (e.g., https://api.staging.com) - stored per environment
  • path: The remaining path (e.g., /api/v1/users) - stored as the endpoint path

During execution, the system dynamically reconstructs the full URL based on the selected environment's baseUrl configuration.

If the same API is recorded from different environments (DEV vs STAGING), the system merges the baseUrls into a map: { DEV: "...", STAGING: "..." }. This is the "Intelligent Upsert" mechanism.
7. Recording Toolbar UI

The injected toolbar provides user controls for managing the recording session.

UI Components:

  • Status Indicator: Red dot when recording, gray when paused.
  • Mode Dropdown: Switch between UI Steps, API Requests, Elements Only. Disabled while recording.
  • Start/Pause Button: Toggle recording state. Shows "▶ Start" when paused, "⏸ Pause" when recording.
  • Badge: Bottom-center hint "Right-Click an element to Record" - only visible in Elements mode.

State Synchronization:

When user interacts with the toolbar, the browser updates __recorderState and calls onRecorderStateChanged() to notify the server. The server uses this state to filter what gets recorded.

8. Stop Recording

When recording stops, the system cleans up browser resources.

Cleanup Process (engine.ts stopRecording):

  1. Close the active browser instance
  2. Set activeBrowser to null
  3. Set activePage to null

Note: The recorded elements and steps remain in the project's repository - only the browser is closed.
