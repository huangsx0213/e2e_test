Execution Logic

QuantumQA Test Runner - Complete Technical Guide

About This Document

This document describes the execution logic of QuantumQA's test runner. The runner is responsible for orchestrating test execution across different levels: Plan → Scenario → Suite → Case → Step.

Key Concepts:

  • Execution Types: 4 ways to start tests (case, suite, scenario, plan)
  • DataSource Strategy: Determines where test data comes from (scenario variables vs suite dataRows)
  • Variable Scopes: 13-layer priority system for variable resolution
  • Dynamic Variables: Runtime value generation with different caching strategies
  • Lifecycle: Setup → Steps → Teardown with proper cleanup
1. Execution Entry Point

When a test execution is triggered via HTTP POST to the execute endpoint, the system goes through several critical steps to prepare and initiate the run.

Entry Process (runner.ts startExecution):

  1. Queue Check: The runner maintains a single-execution queue. If an execution is already running, it rejects the new request with an error message.
  2. ID Generation: Generates unique identifiers - runId for internal tracking and reportId for results retrieval.
  3. Database Record: Creates an execution_run record in the database to track progress, including the type of execution, project ID, target environment, and relevant IDs.
  4. Logger Setup: Creates an ExecutionLogger instance associated with the report ID for real-time log streaming.
  5. Async Execution: The actual test execution runs asynchronously in the background. The HTTP endpoint returns immediately with the reportId, allowing the client to poll for results or stream logs via WebSocket.

2. Core Execution Flow

After the entry point, executeRunAsync performs the actual work of loading data and dispatching to the appropriate handler based on execution type.

Data Loading Sequence:

  1. Project Loading: Retrieves the complete project configuration including scenarios, suites, modules, pages, and all test assets.
  2. API Assets Loading: Filters and loads API-related assets (headers, bodies, endpoints) specific to the current project. These are needed for any API test execution.
  3. Environment Variables: Loads environment-specific variables based on the selected environment (DEV, STAGING, PROD). These typically include base URLs and environment-specific credentials.
  4. Dynamic Variables Initialization: Loads project-level dynamic variables and initializes them based on their evaluation strategy. Variables with ONCE_PER_RUN strategy are evaluated immediately and cached, while others retain their expressions for runtime evaluation.

Handler Dispatch:

Based on request.type, the system dispatches to one of four handlers. Each handler has different data iteration behavior controlled by the dataSource parameter.

3. Case Lifecycle

The case is the atomic execution unit. When executing a single case, the system follows a complete lifecycle that includes suite-level and case-level setup and teardown.

flowchart LR SS[Suite Setup] --> CS[Case Setup] --> MS[Main Steps] --> CT[Case Teardown] --> ST[Suite Teardown] style SS fill:#ddf4ff style MS fill:#dafbe1 style ST fill:#fff8c5

Detailed Lifecycle:

  1. Context Initialization: Creates an ExecutionContext by extracting suite default variables and merging with the first dataRow (or empty object). This context holds all variable layers throughout execution.
  2. Suite Setup: Executes suite.setupSteps if defined. This runs exactly once before the first case in the suite. Use for prerequisites like logging in or initializing test data.
  3. Case Setup: Executes testCase.setupSteps if defined. This runs before each case execution. Use for case-specific preparation.
  4. Main Steps Execution: The core test actions are executed via executeSteps. This processes each step in sequence, handling RUN_MODULE, WAIT, API, and UI actions.
  5. Case Teardown: Executes testCase.teardownSteps if defined. Runs after each case for cleanup like logging out or clearing session data.
  6. Suite Teardown: Executes suite.teardownSteps if defined. Runs exactly once after all cases complete. Use for final cleanup like closing browser pages.
  7. Variable Cleanup: Finally, clears CASE-scoped variables and ONCE_PER_CASE dynamic variable caches to prevent data leakage to subsequent executions.
Even when running a single case, the entire Suite Setup and Teardown phases still execute to ensure proper initialization and cleanup.
4. Suite Execution & DataSource Strategy

When executing a suite or scenario, the system iterates through dataRows and cases. The DataSource strategy determines which data takes precedence.

DataSource Logic:

The dataSource parameter is passed to runSuiteWithContext and controls how dataRows are determined:

SCENARIO Scenario-Driven (Default)

When dataSource is SCENARIO, the system ignores Suite's own dataRows by forcing dataRows to [{}]. This prevents data multiplication when scenario variables drive the execution.

This is the default for scenario and plan execution, designed for centralized data management where the scenario defines all test data.

SUITE Suite-Driven (Default for Suite)

When dataSource is SUITE, the system uses the Suite's own dataRows directly. Each suite can have independent test data.

This is the default when running a suite directly, designed for standalone suite execution with self-contained data.

Nested Iteration Structure:

The suite execution uses a two-level nested loop structure. The outer loop iterates through DataRows, and for each DataRow, the inner loop executes all Cases. This means if you have 3 cases and 2 DataRows, you get 6 total case executions.

For each DataRow iteration, a fresh ExecutionContext is created with the current row's data. After completing all cases for a DataRow, suite-level teardown runs and variables are cleared via clearSuiteVars().

5. Variable Scope Priority

QuantumQA implements a sophisticated 13-layer variable priority system that determines which value takes precedence when the same variable key exists in multiple sources.

flowchart LR D[DYNAMIC] --> E[ENV] --> RE[RUN_ENV] --> SU[SUITE] SU --> SD[SUITE_DATA] --> RS[RUN_SUITE] --> MD[MODULE_DEFAULT] MD --> SC[SCENARIO] --> SN[SCENARIO_DATA] --> RN[RUN_SCENARIO] RN --> OV[OVERRIDE] --> CO[CALLER_OVERRIDE] --> CA[CASE] style D fill:#f6f8fa style CA fill:#ffebe9

Layer Descriptions (Low to High):

  1. DYNAMIC: Project-level dynamic variables defined in configuration. These are evaluated at runtime using generators like $uuid(), $timestamp(), etc.
  2. ENVIRONMENT: Environment-specific configuration variables like BASE_URL, API_KEY, etc. These are consistent across the entire environment.
  3. RUNTIME_ENVIRONMENT: Variables extracted at runtime with ENV scope. Set during execution from API responses or UI elements.
  4. SUITE: Static default variables defined in the Suite configuration. Applied to all cases within the suite.
  5. SUITE_DATA: Current iteration's dataRow values from the Suite's data-driven testing configuration.
  6. RUNTIME_SUITE: Variables extracted at runtime with SUITE scope. Shared across cases within a DataRow iteration.
  7. MODULE_DEFAULT: Default parameter values for Test Modules. Applied when RUN_MODULE is executed.
  8. SCENARIO: Static default variables from Scenario configuration. Applied to all suites in the scenario.
  9. SCENARIO_DATA: Current iteration's dataRow values from the Scenario.
  10. RUNTIME_SCENARIO: Variables extracted at runtime with SCENARIO scope. Shared across suites within a scenario iteration.
  11. OVERRIDE: Manual variable overrides provided during execution request.
  12. CALLER_OVERRIDE: Explicit parameter overrides when calling RUN_MODULE.
  13. CASE (Highest): Variables extracted at runtime with CASE scope. Set during step execution and have highest priority.

Resolution Logic:

When resolving a variable, the system walks through layers in reverse order (highest to lowest). The first match wins, meaning higher priority layers override lower ones.

6. Dynamic Variable Strategies

Dynamic variables provide runtime value generation using built-in generators like $uuid(), $timestamp(), $random(), etc. Their evaluation strategy controls when and how often they're resolved.

StrategyBehaviorWhen Cleared
ONCE_PER_RUN Evaluated once at execution start and cached globally. Same value used throughout entire execution. Never - persists for entire run
EVERY_TIME Re-evaluated on every reference. Generates fresh value each time the variable is used. Never - always recalculated
ONCE_PER_CASE Evaluated once per case and cached. Same value used within a single case execution. After each case completes (clearCaseVars)
ONCE_PER_SUITE Evaluated once per DataRow iteration and cached. Same value used for all cases in current DataRow. After each DataRow completes (clearSuiteVars)
ONCE_PER_SCENARIO Evaluated once per scenario DataRow iteration. Value is shared across all suites in the scenario. After scenario iteration completes (clearScenarioVars)
The ONCE_PER_SCENARIO strategy enables cross-suite data sharing within a scenario. Variables are passed via sharedDynamicCaches between suite executions.
7. Step Execution Types

Steps are the atomic actions that make up a test case. The executeSteps function iterates through steps and dispatches based on action type.

flowchart LR S[Step] --> T{Action Type} T -->|RUN_MODULE| M[Find Module → Recurse → Merge] T -->|WAIT| W[Parse ms → setTimeout] T -->|API_| A[HTTP → Assert → Extract] T -->|UI_| U[Playwright → SmartWait → Extract] style M fill:#dafbe1 style A fill:#fff8c5 style U fill:#ffebe9

Step Type Details:

  1. RUN_MODULE: Executes a reusable Test Module. The system finds the module by ID, validates recursion depth (max 20), creates a sandboxed child context with module parameters, recursively executes module steps, and merges extracted variables back to parent context with optional namespace prefix.
  2. WAIT: Pauses execution for a specified duration. Parses the data field as milliseconds and uses setTimeout to delay before continuing to next step.
  3. API_GET/POST/PUT/DELETE: Executes HTTP API requests. Resolves endpoint URL, headers, and body using variable interpolation, sends request via api-executor, validates response assertions, and extracts variables from response.
  4. UI_* (CLICK, TYPE, HOVER, etc): Executes browser UI actions via Playwright. Lazily initializes Playwright browser context if needed, executes the specified action, performs Smart Wait assertions for reliable testing, optionally captures screenshots, and extracts variables from UI elements.
8. Variable Cleanup

Proper cleanup prevents variable leakage between test executions. Each scope has its own cleanup method that clears variables and dynamic variable caches.

flowchart LR CD[Case Done] --> CC[clearCaseVars] DD[DataRow Done] --> CS[clearSuiteVars] SD[Scenario Done] --> SC[clearScenarioVars] style CC fill:#ffebe9 style CS fill:#fff8c5 style SC fill:#dafbe1

Cleanup Details:

MethodWhen CalledClears
clearCaseVars() After each case completes CASE layer + ONCE_PER_CASE caches
clearSuiteVars() After each DataRow iteration RUNTIME_SUITE layer + ONCE_PER_SUITE caches
clearScenarioVars() After scenario DataRow iteration RUNTIME_SCENARIO layer + ONCE_PER_SCENARIO caches

The cleanup ensures that variables extracted in one case don't affect subsequent cases, and dynamic variables with scoped strategies are properly regenerated when needed.

9. Cross-Suite Variable Sharing

Within a single scenario DataRow iteration, variables can be shared between suites. This enables workflows where output from one suite (like a created user ID) can be used by subsequent suites.

Sharing Mechanism:

  1. Shared Runtime Variables (sharedRuntimeVars): Stores variables extracted with SUITE or SCENARIO scope during execution. These are injected into each suite's context and persist across suites within the same iteration.
  2. Shared Dynamic Caches (sharedDynamicCaches): Stores evaluated ONCE_PER_SCENARIO dynamic variables. These maintain their cached values across suite boundaries.
  3. Iteration Boundary: Both containers are created fresh for each scenario DataRow iteration. When moving to the next DataRow, new containers are created and previous shared values are discarded.

Example Use Case:

Suite 1 creates a user via API and extracts userId to sharedRuntimeVars. Suite 2 performs actions as that user by referencing the shared userId. Both suites execute within the same scenario DataRow iteration.
